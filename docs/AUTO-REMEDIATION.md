# Approval-Gated Auto-Remediation

DevShield v1.6 extends the agentic security engine with exact remediation proposals and an explicit local approval gate.

## Safety model

The GitHub Action **never modifies repository source files**. During CI it can inspect the current workspace and emit:

- `.devshield/devshield-remediation-plan.json`
- `.devshield/devshield-remediation-plan.md`

A local operator can then inspect the proposal and apply only the allowlisted exact edits:

```bash
npm run remediate
npm run remediate -- --apply --approve <missionId> --dry-run
npm run remediate -- --apply --approve <missionId>
npm run scan -- --repository --fail-on high
```

The approval value must match the stable mission ID generated by the agentic scan.

## Exact-edit allowlist

v1.6 intentionally keeps the mutation surface small. It can propose/apply only source-line edits where the intended hardening value is unambiguous:

- `debug-mode`: explicit `debug: true` / `DEBUG=true|1` → disabled
- `k8s-privileged`: `privileged: true` → `false`
- `allow-privilege-escalation`: `allowPrivilegeEscalation: true` → `false`
- `disabled-tls`: explicit Node TLS verification disablement → enabled

All secrets, authentication, injection, dependency, CI permission, package pinning and semantic code changes remain human-only.

## Anti-stale and filesystem protections

Before an approved write, DevShield verifies:

- repository-relative paths only;
- no symlink path;
- text file and size limits;
- the source line is still exactly the one that was reviewed;
- the SHA-256 line hash matches the proposal;
- the proposal is bound to the approved mission ID.

If source changed after the plan was created, the apply step aborts and requires a fresh scan.

## Verification loop

Applying a candidate is not treated as proof of remediation. After any approved local edit, rerun DevShield. The finding fingerprint must disappear from the new-finding set and any relevant application/platform tests should also pass before merge.
